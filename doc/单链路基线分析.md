# 订单链路基线分析

> 基于当前代码库梳理：用户下单主流程、订单状态与流转、库存/积分/购物车/权限关系、用户与管理员操作边界、异常与限制。  
> 文件名「单链路基线」与「订单链路」同指本订单全链路基线。

---

## 1. 用户下单主流程（后端）

1. **鉴权**：`POST /orders` 不在 `AuthMiddleware` 白名单，需带 `Authorization: Bearer <JWT>`，由 `userId` 识别用户。
2. **数据来源**：从**当前用户购物车**中筛选 `isSelected == 1` 的行（`CartRepository.findByUserId` + 内存过滤）。
3. **校验**
   - 至少有一条选中商品，否则：`RuntimeException("购物车中没有选中的商品")`。
   - 每件商品：`Product` 存在；`stock >= quantity`，否则报库存不足。
   - 汇总积分 `totalPoints = Σ(pointsRequired × quantity)`。
   - 用户 `points >= totalPoints`，否则报积分不足。
   - 若请求体带 `addressId`：地址记录必须存在；**未校验地址是否属于当前用户**。
4. **落库与副作用**（`OrderService.createOrder`，`@Transactional`）
   - 新建 `Order`：`status = "pending"`，写入收货快照（有地址时）、`totalPoints`、`remark`。
   - 批量写入 `OrderItem`。
   - **扣库存、加销量**：按行更新 `Product`。
   - **扣积分**：`UserService.updatePoints(userId, -totalPoints)`。
   - **积分流水**：`PointsHistory`，`type = "spend"`，`relatedType = "order"`。
   - **删除**已下单对应的购物车行（仅删除参与结算的选中项）。

**前端**：购物车「结算」跳转到 `/orders/create`，**路由表中无该路径**；全仓库仅 `orderApi.createOrder` 定义，**没有任何页面调用下单接口**——当前产品层面「一键下单」未接通。

## 2. 订单状态与状态流转

| 状态值       | 含义（与前端文案一致） |
|-------------|------------------------|
| `pending`   | 待处理                 |
| `processing`| 处理中                 |
| `shipped`   | 已发货                 |
| `completed` | 已完成                 |
| `cancelled` | 已取消                 |

**创建**：下单成功即为 `pending`。

**用户侧**

- `PUT /orders/{id}/cancel`：`cancelOrder` 仅当 `status === "pending"` 且订单属于当前用户；成功后设为 `cancelled`，并退款积分、恢复库存与销量。
- **非 `pending` 不可由用户取消**。

**管理员侧**

- `PUT /admin/orders/{id}/status`，body：`{ "status": "<任意字符串>" }`。
- `AdminService.updateOrderStatus` **直接 `order.setStatus(status)`，无合法状态校验、无与 `cancelled` 等业务规则联动**。

**理论上的流转**（仅靠约定 + 管理端下拉）：  
`pending` → `processing` → `shipped` → `completed`；`pending` 还可经用户取消 → `cancelled`。  
管理员也可把状态改成任意值（含非法或倒退），**与库存/积分无二次校验**。

## 3. 与库存、积分、购物车、权限的关系

| 维度       | 行为 |
|------------|------|
| **库存**   | 下单成功即扣减、加销量；用户取消 `pending` 订单则回补库存、回冲销量。管理员改状态**不**自动调整库存。 |
| **积分**   | 下单扣减并记 `spend` 流水；用户取消 `pending` 返还并记 `refund` 流水。管理员改订单状态**不**触发积分变化。 |
| **购物车** | 仅结算**选中**（`isSelected=1`）的条目，结算后**删除这些购物车行**；未选中条目保留。 |
| **权限**   | 普通用户：`/orders*` 需登录，仅能操作/查看自己的订单。管理员：`/admin/orders` 等需登录且 Controller 内校验 `role === "admin"`；**JWT 仍用同一套 Filter**，无单独「管理员接口」白名单。 |

**购物车勾选**：实体有 `isSelected`，`CartService.getCartSummary` 与下单逻辑均依赖该字段，但 **Cart API 无更新 `isSelected` 的接口**，前端 `toggleSelect` 仅 `loadCart()`，**无法真正改勾选**；默认新加购为选中，故多数情况下等于「整单全选结算」。

## 4. 用户侧与管理员侧可操作范围

**用户（已登录）**

- `POST /orders`：创建订单（需购物车有选中商品且通过校验）。
- `GET /orders`：自己的订单列表（`deletedAt IS NULL`）。
- `GET /orders/{id}`：自己的订单详情 + 明细。
- `PUT /orders/{id}/cancel`：仅 **自己的、且 `pending`** 订单取消。

**前端页面**：我的订单列表、详情、取消（与上述一致）；**无实现的下单页**。

**管理员**

- `GET /admin/orders`：全量订单（`findAll()`，**含已逻辑删除或跨用户，以仓库实现为准**）。
- `PUT /admin/orders/{id}/status`：改状态（无业务规则约束）。

**前端**：后台订单列表可改状态下拉（选项含 pending～completed，**无 cancelled**；与后端可写任意字符串不一致）。

## 5. 异常分支与实现限制

**下单失败（`ORDER_001`，400）**

- 购物车无选中商品；商品不存在；库存不足；积分不足；用户不存在；地址 id 存在性失败。
- **未校验**：商品是否上架/删除（`Product.status` 等若存在未在 `OrderService` 中使用）；地址是否属于当前用户。

**用户取消失败**

- 订单不存在；非本人；非 `pending`。

**并发与一致性**

- 依赖事务与单次读库存；高并发下典型「超卖」风险未用乐观锁/版本号处理。

**软删除**

- `Order` 有 `deletedAt`，列表用 `findByUserIdAndDeletedAtIsNull`，但 **`getOrderById` 用 `findById`，不区分已删订单**（若业务会写 `deletedAt`，详情可能仍可读）。

**积分流水**

- `balanceAfter` 在扣款/退款时用下单/取消前内存中的 `user.getPoints()` 推算，与 `updatePoints` 顺序一致，逻辑自洽。

**前端/产品缺口**

- `/orders/create` 无路由，**结算无法完成下单**。
- 购物车勾选无效，与「部分结算」设计不一致。

**管理端**

- 状态可任意修改；从 `cancelled` 再改为 `processing` 等无拦截；与库存、积分不同步。

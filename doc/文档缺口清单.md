### 1.3 代码注释

| 观察 | 说明 |
|------|------|
| **密度低** | 多数类/方法无 Javadoc；实体上偶有字段语义注释（如 `Order.status` 枚举示意） |

## 3. 哪些缺口会影响后续测试设计与变更实施

### 3.1 对测试设计的影响

| 缺口 | 影响 |
|------|------|
| **无统一接口契约** | 用例需从代码反推路径与字段，**易漏测**；前后端不一致时**难以判定缺陷归属** |
| **无产品级状态规则** | 订单等场景**无法写「应然」断言**，只能对齐「当前实现」（含管理员任意改状态） |
| **无错误码表** |  negative 测试的**期望 HTTP 体/码**不稳定 |
| **无非功能指标** | 性能、并发、安全测试**无通过标准** |
| **订单分析文档已列 H1～H11 类矩阵** | 可支撑**部分**集成测试设计，但**全模块**仍缺等价矩阵 |

### 3.2 对变更实施的影响

| 缺口 | 影响 |
|------|------|
| **无 Me2AI 需求锚点** | 需求变更时**易与实现漂移**，评审缺少对照物 |
| **无 AI2AI 协议/数据同步** | 改表或改 API 时，**依赖人工记得更新多处**，易遗漏前端/联调方 |
| **无架构决策记录（ADR）** | 重大技术选型（为何 SQLite、为何 Filter 鉴权等）**无记录**，后续替换成本高 |
| **根 README 缺失** | 新人/CI ** onboarding 路径不清**（需依赖 `doc/项目初始化摘要`） |
| **OpenSpec 与 spec 双层关系** | `openspec` 管变更，**全量协议若不回填 `spec/AI2AI`**，仍会出现**文档与代码双轨** |

### 3.3 建议优先级（补救顺序）

1. **恢复或新建 `spec/Me2AI/` 最小集**（需求描述、技术约束）——变更与测试的**需求锚点**。  
2. **维护 `spec/AI2AI/协议和数据.md`**（或与 `doc` 明确「主副本」关系）——**接口与表结构单一事实来源**。  
3. **根目录 `README.md` 链到 `doc/项目初始化摘要.md` + 启动命令**——降低协作摩擦。  
4. **错误码 + 订单（及扩展至全局）状态机**——支撑自动化测试断言与回归范围。  
5. **将订单路基线分析中的「漏洞/缺口」转入缺陷或技术债 backlog**——避免仅停留在文档。

## 4. 小结

| 维度 | 完备性概括 |
|------|------------|
| **本地运行与模块鸟瞰** | 较好（`项目初始化摘要` + 配置） |
| **订单域深度** | 较好（两份单链路基线文档） |
| **全站需求 / 协议 / 状态 / 测试基线** | **弱**；`spec` 空、根 README 缺、接口与错误码无总表 |
| **对测试与变更的影响** | **高**：缺少契约与需求锚点会直接增加**用例维护成本**与**回归范围不确定性** |

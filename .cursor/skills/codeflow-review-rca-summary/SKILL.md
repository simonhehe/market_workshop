## 07 — 代码审查

### 使用场景

当需要审查 AI 生成代码、人工代码或 Pull Request 时，使用本小节。

### 角色

你是一名严格但建设性的资深代码审查者。

### 输入

根据以下内容审查选中的代码或 diff：OpenSpec 需求、设计方案、既有架构、团队编码规则、测试要求。

### 审查维度

1. 需求一致性
2. 架构与分层
3. API 兼容性
4. 数据库影响
5. 测试覆盖
6. 安全性
7. 可维护性
8. 性能风险
9. 回归风险

### 输出格式

#### 审查总结

#### 问题清单

| 严重级别 | 位置 | 问题 | 风险 | 建议修复 |
|---|---|---|---|---|

严重级别：Blocker、Major、Minor、Suggestion。

#### 缺失测试

| 需求 / 场景 | 缺失测试 | 建议测试层级 |
|---|---|---|

#### 合入建议

选择一个：可以合入 / 小问题修复后可合入 / 必须修复后再合入。

## 08 — RCA 分析

### 使用场景

当需要分析 Bug、生产问题、测试失败、回归问题或交付问题时，使用本小节。

### 角色

你是一名根因分析专家。

### 输入

使用：Bug 描述、错误日志、失败测试、相关代码、相关 OpenSpec 需求、近期变更。

### 任务

分析根因，并提出修复方案和预防动作。

### 必须步骤

1. 总结现象。
2. 识别影响范围。
3. 追踪可能原因。
4. 识别根因。
5. 提出代码修复方案。
6. 提出测试修复方案。
7. 提出流程或规则改进。

### 输出格式

#### 现象

#### 影响范围

#### 时间线 / 触发条件

#### 根因

#### 证据

#### 修复计划

| 动作 | 层级 | 负责人 | 优先级 |
|---|---|---|---|

#### 回归测试

| 场景 | 测试层级 | 预期结果 |
|---|---|---|

- Rule 更新：
- OpenSpec 更新：
- 测试策略更新：
- 监控或日志更新：

# 业务测试用例：用户结算下单与订单状态筛选

> **变更 ID**：`add-user-checkout-and-order-filter`  
> **依据**：`proposal.md`、`design.md` §4～§5、`doc/smoke-checkout-order-filter.md`  
> **用途**：手工/探索性业务测试、UAT 清单；与 **Smoke**（最短路径）、**白盒**（`whitebox-matrix.md`）分工互补。

---

## 1. 测试范围与前置

| 项 | 说明 |
|----|------|
| **In Scope** | 购物车勾选与结算闭环、结算页提交、`GET /orders?status=` 筛选、下单时 `addressId` 归属校验、购物车行归属（IDOR 修复） |
| **Out of Scope** | 管理员流程重定义、支付/物流、并发库存乐观锁（见 proposal） |

| **账号** | 普通用户：`user1` / `password1`；需越权场景时准备第二用户（如 `user2`）及各自地址数据 |

## 3. 详细用例

### 3.1 购物车勾选与持久化

#### BTC-01 【P0】行勾选生效且汇总更新

| 项 | 内容 |
|----|------|
| **重点** | `PUT /cart/{id}/selection` 与前端联动，`summary.selectedCount`、`totalPoints` 正确 |
| **前置** | 已登录；购物车至少 1 条商品行 |
| **步骤** | 1. 打开购物车，记录当前「已选件数」与合计积分。<br>2. 勾选一行商品（若默认未选）。<br>3. 观察汇总区是否更新。<br>4.（可选）用 API：`GET /api/cart`，确认该行 `isSelected` 与 `summary` 一致。 |
| **验收条件** | ① 勾选后 `selectedCount` 增加、合计积分与选中行一致。<br>② 无前端报错，接口 200。 |

#### BTC-02 【P0】取消勾选后不可单独依赖「结算」

| 项 | 内容 |
|----|------|
| **重点** | 无选中商品时不得完成结算（按钮禁用或明确提示） |
| **前置** | 已登录；购物车有商品 |
| **步骤** | 1. 全部取消勾选。<br>2. 查看「去结算」是否禁用或点击后提示「请选择要结算的商品」类文案。<br>3. 直接访问 `/checkout`（若允许进入），提交订单应失败或页面提示无选中项。 |
| **验收条件** | 与 design §1「无选中项」一致；不得在无选中情况下成功创建订单。 |

#### BTC-03 【P1】勾选状态刷新后保持

| 项 | 内容 |
|----|------|
| **重点** | AC-F5：持久化与刷新一致 |
| **前置** | BTC-01 已勾选至少一行 |
| **步骤** | 1. 勾选/取消勾选若干行。<br>2. 刷新浏览器（F5）。<br>3. 再次进入购物车。 |
| **验收条件** | 各行勾选状态与刷新前一致，`summary` 正确。 |

#### BTC-04 【P1】他用户不可改我购物车行（归属）

| 项 | 内容 |
|----|------|
| **重点** | `updateQuantity` / `removeFromCart` / `selection` 均校验 `cart.userId` |
| **前置** | user1 有一条购物车行 id=`C1`；登录 user2 |
| **步骤** | 1. 使用 user2 的 Token 调用 `PUT /api/cart/C1/selection`（或改数量、删除）。 |
| **验收条件** | 400 或 403，**不得**修改 user1 的购物车数据；user1 侧数据不变。 |

### 3.2 结算页与下单

#### BTC-05 【P0】主路径：勾选 → 结算 → 下单成功

| 项 | 内容 |
|----|------|
| **重点** | AC-F1：闭环与订单 `pending`、已结算行从购物车移除 |
| **前置** | 已登录；积分 ≥ 选中商品所需积分；商品库存充足 |
| **步骤** | 1. 购物车勾选至少一件。<br>2. 点击「去结算」→ 进入 **`/checkout`**。<br>3. 确认展示选中商品摘要、合计积分；可选填备注、选择地址（若有）。<br>4. 提交订单。<br>5. 记录跳转页（订单详情 `/orders/:id` 或列表）。<br>6. 返回购物车，确认已下单商品行已移除或数量扣减符合设计。 |
| **验收条件** | ① 新订单 `status=pending`。<br>② 购物车已结算行处理符合 `OrderService.createOrder` 既有行为（通常移除选中行）。<br>③ 用户积分与库存变化符合业务规则（与现网一致）。 |

#### BTC-06 【P0】积分不足

| 项 | 内容 |
|----|------|
| **重点** | AC-F2：`ORDER_001` 类错误，无部分扣款 |
| **前置** | 用户积分低于选中商品所需总积分（可通过管理员改积分或选高价商品构造） |
| **步骤** | 1. 勾选商品使所需积分 > 当前积分。<br>2. 尝试结算并提交（或仅后端 `POST /orders`）。 |
| **验收条件** | 提交失败，提示与后端错误码/文案一致；**无**订单生成、**无**积分扣除、**无**库存扣减。 |

#### BTC-07 【P1】库存不足

| 项 | 内容 |
|----|------|
| **重点** | AC-F2 同类：失败完整、无部分成功 |
| **前置** | 选中商品库存不足以满足数量（依赖数据或管理端调库存） |
| **步骤** | 1. 加购至超库存或保持选中。<br>2. 提交订单。 |
| **验收条件** | 失败提示明确；无部分扣款/无脏订单。 |

#### BTC-08 【P1】未选中商品调用下单接口

| 项 | 内容 |
|----|------|
| **重点** | 后端对「无选中行」下单的约束 |
| **前置** | 购物车有商品但全部 `isSelected=0` |
| **步骤** | 直接 `POST /api/orders`（带合法 Token）。 |
| **验收条件** | 400 等业务失败，提示说明无选中商品或等价语义。 |

#### BTC-09 【P2】结算页展示与地址可选

| 项 | 内容 |
|----|------|
| **重点** | design §3：地址非必填时仍可提交 |
| **前置** | 用户可无地址或有多条地址 |
| **步骤** | 1. 无地址时提交（若产品允许）。<br>2. 有多条地址时切换选择再提交。 |
| **验收条件** | 与产品约定一致；成功订单中 `addressId` 与选择一致或为空规则一致。 |

### 3.3 地址安全

#### BTC-10 【P0】使用他人 addressId 下单被拒绝

| 项 | 内容 |
|----|------|
| **重点** | AC-F3：后端 `address.userId == currentUserId` |
| **前置** | user2 有一条地址 id=`A2`；登录 **user1** |
| **步骤** | 1. user1 购物车有选中商品且可下单。<br>2. `POST /api/orders`，body 含 `"addressId": A2`（user2 的地址）。 |
| **验收条件** | 400（或约定错误码），`message` 含 **「无权使用该收货地址」** 或等价表述；**无**成功建单。 |

#### BTC-11 【P1】使用本人 addressId 下单成功

| 项 | 内容 |
|----|------|
| **重点** | 正例覆盖地址校验不误杀 |
| **前置** | user1 有地址 id=`A1` |
| **步骤** | `POST /api/orders`，`"addressId": A1`，其余同 BTC-05。 |
| **验收条件** | 200，订单关联地址为 `A1`（若实体/接口可核对）。 |

---

### 3.4 订单列表筛选

#### BTC-12 【P0】按「待处理」仅见 pending

| 项 | 内容 |
|----|------|
| **重点** | AC-F4 |
| **前置** | 当前用户同时存在多种状态订单或至少一条 `pending` |
| **步骤** | 1. 打开「我的订单」。<br>2. 选择筛选「待处理」/ `pending`（与 UI 文案一致）。 |
| **验收条件** | 列表中每条订单 `status` 均为 `pending`；非 pending 不出现。 |

#### BTC-13 【P0】「全部」与不带参数一致

| 项 | 内容 |
|----|------|
| **重点** | AC-F4：`status` 省略或 `all` |
| **前置** | 有多状态订单更易观察 |
| **步骤** | 1. 筛选「全部」。<br>2. 对比直接调用 `GET /api/orders` 无 query。 |
| **验收条件** | 两种结果集一致（未删除订单全集）。 |

#### BTC-14 【P1】各状态筛选项（若 UI 提供）

| 项 | 内容 |
|----|------|
| **重点** | `processing|shipped|completed|cancelled` 与后端一致 |
| **步骤** | 逐个切换状态 Tab/下拉，抽样核对 API `GET /orders?status=xxx`。 |
| **验收条件** | 列表订单状态与筛选值一致；空列表时空态合理（见 C3）。 |

### 3.5 回归与其它

#### BTC-15 【P0】pending 订单可取消且积分/库存恢复

| 项 | 内容 |
|----|------|
| **重点** | AC-R1 |
| **前置** | 有一条 `pending` 订单 |
| **步骤** | 1. 在列表或详情点击「取消订单」。<br>2. 核对订单状态变为 `cancelled`（或项目约定终态）。<br>3. 核对用户积分与商品库存恢复与现有逻辑一致。 |
| **验收条件** | 与变更前行为一致，无回归。 |

#### BTC-16 【P2】非 pending 不展示「取消订单」

| 项 | 内容 |
|----|------|
| **重点** | design §4 按钮可见性 |
| **前置** | 有非 pending 订单 |
| **步骤** | 打开列表/详情，查看「取消订单」按钮。 |
| **验收条件** | **仅** `pending` 显示取消；其它状态不显示或不可用。 |

#### BTC-17 【P0】未登录访问结算页

| 项 | 内容 |
|----|------|
| **重点** | AC-R2 |
| **前置** | 浏览器无登录态或清除 Token |
| **步骤** | 访问 `/checkout`。 |
| **验收条件** | 跳转登录页或等价鉴权流程，无法在登录前完成下单。 |

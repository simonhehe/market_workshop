# 订单创建与校验

## ADDED Requirements

### Requirement: 下单必须要求有效且归属本人的地址

`POST /api/orders` 必须接收 `addressId` 与可选 `remark`；`addressId` 缺失返回 `ADDR_REQUIRED`，不存在、已删除或不属于当前用户返回 `ADDR_NOT_FOUND`，且不得创建订单或产生扣减。

#### 场景：未传地址
- **当** 用户提交不含 `addressId` 的请求
- **则** 返回 `ADDR_REQUIRED`，订单、积分、库存、购物车均不变

#### 场景：使用他人地址
- **给定** 地址属于另一用户
- **当** 用户提交该 `addressId`
- **则** 返回 `ADDR_NOT_FOUND`，不泄露地址信息且不下单

### Requirement: 服务端必须按固定优先级校验

服务端必须依次校验：选中项非空 → 地址 → 商品存在且 active → 库存 → 积分；任一失败返回对应业务键，且不产生任何写入。

#### 场景：空购物车
- **当** 无选中项时提交
- **则** 返回 `CART_EMPTY`

#### 场景：商品下架
- **给定** 选中商品 `status=inactive`
- **当** 提交订单
- **则** 返回 `PRODUCT_UNAVAILABLE`，无扣减

#### 场景：库存不足整单回滚
- **给定** 两件选中商品，其中一件库存不足
- **当** 提交订单
- **则** 返回 `STOCK_INSUFFICIENT`，两件商品的库存、用户积分、购物车均不变，不生成订单

#### 场景：积分不足
- **给定** 用户余额低于应付合计
- **当** 提交订单
- **则** 返回 `POINTS_INSUFFICIENT`，消息包含当前积分、应付与差额，无扣减

### Requirement: 下单必须在单事务内落库并生成快照

成功下单必须在同一事务内：创建 `Order`（强制 `pending`、服务端计算 `totalPoints`、地址快照、唯一 `orderNo`）、写入 `OrderItem` 快照、扣减用户积分、扣减商品库存并增加销量、写 spend 流水、删除选中购物车项。客户端传入的 `totalPoints`、`status`、`points` 必须被忽略。

#### 场景：正常下单
- **给定** 地址有效、库存与积分充足、存在选中与未选条目
- **当** 提交订单
- **则** 返回 `pending` 订单；选中条目库存减少、销量增加并从购物车删除；未选条目保留；响应含 `id`、`orderNo`、`totalPoints`、`status`

#### 场景：历史快照
- **当** 下单后修改商品名称或单价
- **则** 历史订单项仍展示下单时的名称、单价、数量与小计

#### 场景：客户端伪造字段
- **当** 请求体附带 `totalPoints`、`status` 或 `points`
- **则** 服务端按数据库重算合计并强制 `pending`

### Requirement: 订单号必须唯一

订单号必须由服务端生成且在并发/同毫秒场景下尽力避免碰撞，数据库唯一约束兜底。

#### 场景：连续下单
- **当** 同一用户快速创建两笔订单
- **则** 两笔订单 `orderNo` 不同
